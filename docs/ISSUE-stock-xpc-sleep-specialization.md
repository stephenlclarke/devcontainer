# Stock startup aborts in an optimized XPC timeout child

Exact source `afd74cc2e63f0b3a6de21ddc303e00688665a95e` aborts during Apple stock startup before fixtures. The Engine log reports `freed pointer was not the last allocation`; diagnostic incident `DAE79F15-9CC5-4550-B00E-D7A23E82E591` records `swift_task_dealloc` followed by the timeout child of `XPCClient.send(_:responseTimeout:)`. Startup restores port forwarding by listing containers through Container SDK XPC. The abort occurs about two seconds after startup, before the ten-second list timeout could fire.

The compiled stock SDK binds Container source `9a8917ca2da5cd6ba059b9ba5ca5a74892e9bb7d` and `libContainerXPC.rspm.__impl.a` SHA-256 `e3c075dec4bdbf1074cb613b451ffb7a9b29a5c9056465195677b0af572c53ca`. Its lower Engine API remains `36de2d66d4a1f7eb48c08d94cf1444f93d5f9c77` and Containerization remains `9eacc197d7c3663eb29cbab6d51244ede6d1cd7d`. The new root event retry introduced a generic `Task.sleep(for:)` call. [Swift issue 86204](https://github.com/swiftlang/swift/issues/86204) reports the same allocator failure and stack shape when optimized modules contribute different sleep specializations, with a nanosecond-overload workaround. This is a supported compiler-specialization suspicion, not a proven application timeout or double-resume defect. Binary symbol inspection shows multiple local specialized resume bodies sharing one coalesced async descriptor in both the earlier working and failed binaries; symbol counts alone do not establish causation.
