# Bazel test-harness replacement

Status: implementation in progress, not release qualification. The existing harnesses remain until their replacement covers their complete scenario inventory. The operator explicitly authorised replacing them on 17 September 2026. The new implementation must be simpler, faster, recoverable and at least as comprehensive; wrapping the existing lane-wide runner is not the destination.

## Execution boundaries

| Layer | Owner | Cache and recovery boundary |
| --- | --- | --- |
| Product unit tests | Native Bazel Swift test targets | Declared sources, profile and toolchain; retain the original XML and coverage before output reuse |
| Harness unit and socket-component tests | Native Bazel test targets | Deterministic fixtures; no Container, Docker, credentials, downloads or product builds |
| Process/service integration | Explicit native Bazel integration targets | Fresh execution with a host lease; retain process outcome, cleanup and coverage from that execution |
| Runtime parity | One case, lane and explicit campaign identity | Published release inputs only; never compile a missing reference or candidate; successful independent cases can resume within the same campaign |
| Performance campaign | Fresh uncached live cases under a quiet-host lease | Prefetch first; record all setup, operation and cleanup durations and invalidated samples; do not confuse cached test durations with fresh execution |

Bazel owns dependency scheduling, action reuse, test selection and reports. Small test probes and evidence helpers do not schedule builds, silently retry cases or implement another build coordinator. The first direct Engine probe uses standard-library Python solely as a test client and has no Docker CLI dependency, including in candidate lanes.

## Current replacement components

`Tools/testing/case_evidence.py` seals each case in a transactional SQLite record. Its identity binds the explicit campaign, fixture, lane, contract, harness, release set and runtime fingerprints. Reopening a completed case returns the same authenticated result, including failures. A changed result cannot overwrite it. An unfinished case requires worker/resource reconciliation rather than an automatic restart; other independent case identities remain available. Production admission, artifact fingerprinting, host leases and resource reconciliation must be connected before this evidence component can qualify live campaigns.

Results require separate monotonic setup/operation/cleanup durations, exact observations, explicit errors and cleanup status/resource inventory. Missing observations or uncertain cleanup cannot produce a passing result. The comparator rejects absent or duplicate lanes and mixed campaigns/contracts/releases. It reports ordinary duration ratios separately from functional parity; quiet-host paired performance qualification and its 10x/timeout gate remain to be connected. This component does not claim an arbitrary raw timing observation passed the performance gate.

`Tools/testing/engine_probe.py` replaces E01's Docker-CLI-based HTTP access with direct Unix HTTP. It preserves the five checked-in E01 observations: ping, prefixed API, HEAD ping, unknown-route error envelope and malformed-JSON error envelope. Socket component tests exercise actual HTTP traffic, invalid versions, negative responses, oversized replies, missing endpoints and timeouts. They are tests of the harness, not proof against the three real runtimes.

`Tools/testing/archive_probe.py` ports E05's five archive assertions to direct Unix HTTP: exact content, a 1 MiB binary payload, long filename, exact mode and relative symlink target. It generates deterministic PAX input and inspects the bounded returned tar in memory, never extracting server-supplied paths onto the host. It requires an admitted full container ID and API version; the caller supplies an isolated disposable container, durable resource ownership, a whole-phase deadline and verified cleanup. It does not create a container, pull an image or run Docker. The released guest adapter now connects these boundaries; socket-component success is not live E05 parity. Request timings and sanitized failure types remain available to the case recorder.

`Tools/testing/guest_fixture.py` provides that probe's container ownership boundary. It verifies an already-prepared immutable image ID, refuses existing names, journals creation intent before the request, checks exact returned ID/name/labels/image, starts the guest and connects the archive operation. Removal is by verified immutable ID only; completion requires absent ID/name and an empty owner-label query. An interrupted create can be reconciled when the exact owned resource is observed; a missing response with no observed identity remains uncertain, even after a 404, because creation could still be pending server-side. Interrupted deletion resumes using its retained ID. Journal intent binds the socket and API version as well as the case/image identities. The released adapter supplies the admitted runtime/guest data, host lease, private durable journal and phase deadlines. Component tests exercise the sequence over a real test socket, not a Docker or Apple VM; live qualification remains required. No implicit image pull, compilation or broad cleanup is introduced.

Run the focused native harness checks with `make bazel-harness`. Individual tests and monotonic durations appear in Bazel's JUnit evidence, retained by the existing launcher. Scratch remains on the enrolled SSD. No Swift product compilation is in this target's dependency graph.

`make bazel-prepare-releases` connects the reviewed release-asset lock to executable payloads. Extraction stays on the enrolled SSD; archives and reusable verified executable trees are long-lived internal assets. The existing reference-store lease covers acquisition, preparation and publication. Preparation rejects archive traversal, links, duplicate entries, oversized payloads and missing executables. Apple installer packages are expanded with `pkgutil`, never installed; installer scripts are not executed. Every extracted file and mode is bound into a retained inventory. Executables publish under `~/Library/Application Support/ContainerFamily/retained/workflow/prepared-releases/<preparation-sha>/` with a durable pending intent before copying. Admission refuses pending publication; interrupted copying verifies existing entries, reuses complete files and finishes only owned incomplete files. File/directory durability and complete inventory verification precede removal of the pending marker. Sealed executable trees are never silently repaired or overwritten. Repeated preparation reuses them even after SSD extraction-cache eviction, without re-extraction or compilation. Package expansion does not establish signing/notarization acceptance or prove the complete runtime closure is ready.

This placement follows the long-term asset policy. An SSD-resident stock API executable stalled in `dyld` opening its own binary, while the byte-identical installed internal copy completed a launchd `--help` diagnostic in 0.268 seconds. That comparison is a host-location diagnostic, not parity or permission-policy proof: the later retained-tree integration attempt below still timed out. The workflow retains its own exact release tree rather than trusting the operator's installed tree or changing permissions. Runtime state, native logs, sockets and all disposable test roots remain on SSD.

## Cutover requirements

### Pinned guest image preparation

`make bazel-prepare-guest-images` reads `Tools/bazel/guest-images.lock.json`, downloads only immutable public registry manifests with Homebrew Skopeo (`/opt/homebrew/bin/skopeo`), and creates deterministic OCI archives. It does not use a Docker daemon, start a VM, load images into an operator store or compile products. Skopeo is a data downloader here: acceptance comes from independently checking the pinned manifest/config digests and every referenced blob, not from trusting its reported success. Downloads and repacking use owned SSD staging; completed archives, pending publication records and receipts reside in private internal retained storage. The shared reference-store lease serializes publication. An interrupted copy can be recreated from the identical digest-pinned bytes; a sealed archive is never silently repaired. `make bazel-prepare-guest-images OFFLINE=1` verifies existing complete archives without downloading. Offline preparation can finish a verified receipt's leftover pending marker; runtime admission instead uses `require_image`, which performs no writes and refuses every pending publication.

The OCI closure checker is reused unchanged from Compose commit `c716f013f6380941fd5fd04168ce4fbff5b61027`; provenance and license are in [NOTICE.md](../NOTICE.md). The stock initialization pin is the arm64 image published for Containerization 0.45.0, the dependency of [stock Container 1.4.1](https://github.com/apple/container/blob/1.4.1/Package.resolved). ### First released-service integration target

`make bazel-engine-case CAMPAIGN=<explicit-id> LANE=apple-stock` selects the manual, local, uncached `released_engine_negotiation` target. The enhanced alternative is `LANE=container-compose`. Both use only preprepared release payloads; missing or changed assets fail admission without downloads, extraction or builds. The first adapter explicitly supports the reviewed devcontainer 1.0.1 command interface and does not pass newer service flags to an older binary. This is E01 metadata/protocol integration, not a full guest-runtime campaign or a substitute for the Docker oracle. Docker-lane admission and the other 18 adapters remain unfinished.

The enrolled SSD must enforce file ownership: launchd rejects private service plists on an ownership-disabled volume even when they appear user-owned to the caller. Check with `diskutil info /Volumes/SSD`; an administrator can enable it with `sudo diskutil enableOwnership /Volumes/SSD` after verifying the enrolled volume UUID. The case checks this before suspending services, binds the volume UUID/mount/ownership into its fingerprint, and revalidates it at cleanup. It never changes the mount policy or asks for elevated privileges itself.

The case binds the complete release lock, extracted inventories, actual command versions, OS/architecture, harness and expected observations. Setup and cleanup have separate timings from the conformance operation. The process receives an isolated SSD home/temp directory and a minimal environment. Whole-phase deadlines supplement socket timeouts. Bazel SIGTERM enters cleanup; an interrupted process creation is recorded as uncertain, never reported as no child. The internally retained case seal binds both the result and the exact name/digest inventory of attached diagnostics and ownership records, so missing or changed attachments cannot be reused as a passing result.

Stock Apple Container 1.4.1 connects to the fixed per-user `com.apple.container.apiserver` service; changing `HOME` does not isolate that XPC service. The adapter now selects that service transactionally through `runtime_services.py`: reject active CI workers/container commands/guest processes, snapshot explicitly authorised family jobs, suspend them, prove outgoing process closure, and register the selected prepared API with private SSD application/log/temp roots. The service definition follows stock `SystemStart`'s launchd contract without kernel installation or image pulls. Readiness and cleanup require the exact selected executable and running PID; those fields are attached to the case seal without incorporating transient PIDs into the reusable case identity. No operator provider keys or state are copied or changed. This metadata adapter does not establish the complete guest/runtime closure.

Each protocol request retains its method, route, status or safe exception class, and monotonic duration in `requests.json`, bound into the case seal. Request/response bodies and exception text are not included. This identifies the exact failing endpoint without rerunning a failed case or exposing operator credentials.

Cleanup captures diagnostics even when stopping the owned process fails. `process-cleanup.json` explicitly records whether termination was verified; when false, `engine.log` is a partial snapshot, not a claim that the process stopped. Quarantine remains in place. The Bazel test wrapper sets `BAZEL_TEST=1` itself, so host opt-in checks and declared engine runfiles do not depend on an inherited marker. Negative invocation `3af531b2-2a76-439f-ba53-e766ee0a94e1` verified that both explicit service integration tests fail before their Keychain operations when opt-in is zero; it is deliberate rejection evidence, not a passing integration result.

The adapter acquires the existing per-user Compose runtime lock. Its established `/private/tmp/container-compose-runtime-<uid>.lock` inode remains the shared IPC coordination point; payloads and disposable work stay on SSD. Before launching a service, the adapter writes an internal `runtime-admission.json` ownership marker. It clears that marker only after verified process cleanup, evidence retention, input revalidation and owned-root removal. A surviving descendant, uncertain spawn, hard-killed worker or other unverified cleanup leaves the marker and blocks all later admissions through the new adapter, even with a different campaign ID. Do not delete the marker or invent a fresh campaign to bypass it.

Automatic hard-kill/resource reconciliation is not yet implemented. Legacy Compose/runtime entry points share the lock but do **not** enforce the new quarantine marker: while it exists, keep those entry points suspended too until the owned process/resources are reconciled. Family-wide guard integration is required before unattended live cutover. An ordinary terminal result can be reopened unchanged within its original campaign; failed results cannot be overwritten by a retry.

`service_switch.py` snapshots explicitly authorised definitions before removal, journals every mutation, refuses unknown workloads/foreign replacements, verifies the loaded program and unchanged plist after bootstrap, and restores the original unchanged definitions after partial removal or interrupted registration. Consumers/listeners stop before providers; providers restore before consumers. Process closure is checked before selecting a new provider and before restarting originals. `service_journal.py` supplies an append-only, transactional, owner-bound private SQLite journal with corruption checks. It retains original definitions and bounded API startup-log snapshots in mode-0600 files inside mode-0700 internal storage. Original service environment bytes and API logs can contain credentials: they are never attached to public Bazel evidence; only the journal's hash/count receipt is attached. Original service restoration is attempted even if public diagnostic retention fails after verified engine termination. Root removal and quarantine clearance still require all cleanup and retention to succeed.

Because launchd removal can finish before its processes exit, closure permits a bounded 15-second wait only for disappearing owned processes/registrations. Changed ownership, active unrelated commands and CI workers are not retried. Shared interpreters are tracked by the captured job/descendant PID and start identity, not executable-name equality; `exec` or process-group changes do not end ownership. Homebrew's explicitly registered `sh.brew.container` root process is admitted for suspension only when its definition is exactly `container system start` and the captured PID/start/program still match. No unrelated container command or Actions worker receives that exception.

Simulated-service tests cover successful restoration, unknown workloads, changed/foreign definitions, interrupted removal/registration, a fresh recovery object, parent-driven plugin removal, replacement during bootstrap, outgoing-process survivors, private bounded logs and diagnostics failures. A real subprocess exits mid-SQLite transaction to verify crash rollback and reopen without touching host services. The persistence/switch primitives have focused standard-library trace evidence above 90%; this is diagnostic coverage, not an aggregate product or SonarQube result. Live qualification remains outstanding; do not equate these fault tests with a passing runtime lane.

### Operator service recovery

Run `make bazel-recover-runtime` to inspect the current quarantine under the shared runtime lease. This command does not start Bazel, build a product, change services or execute a parity operation. It verifies the admitted case/ownership artifact, private service journal, original service definitions, enrolled SSD and remaining process inventory. A clear host returns `clear`; a reconcilable journal returns `ready-to-restore` or `ready-to-clear` and its exact case ID. Apply only that identified case with `make bazel-recover-runtime-apply CASE_ID=<reported-case-id>`.

Apply removes only journal-owned selected services, waits for process closure, restores unchanged original registrations, retains bounded native logs privately, and writes a durable cleanup authorization before removing the marked case directory. The authorization binds its device, inode and macOS creation time: a crash during recursive removal can resume even if `owner.json` was already removed, but a replacement directory cannot inherit that authorization. A crash after complete directory removal can clear the guard only after original service registrations and process closure are checked again. Completed case results and seals are never changed; an unfinished case remains unfinished rather than gaining invented phase timings or a passing result.

The command deliberately refuses a live recorded Engine PID/process group, an ambiguous spawn intent without a recorded handle, an unknown client, active CI workers/guest workloads, changed service definitions, missing/corrupt evidence, or older journals lacking the new runtime context. Engine spawn intent is now retained before launch so a worker dying before handle capture cannot be mistaken for a case that never launched a client. These conditions retain quarantine and require explicit process/evidence reconciliation; automatic orphan termination and family-wide guard integration remain unfinished. Original registered service roots can be recognised during resumed cleanup, but their active worker/guest descendants are never exempted. No provider keys are edited and no broad service-stop operation is used.

### Full harness cutover

The existing inventory contains 19 fixtures, each required in all three lanes: E01-E06 Engine semantics, D01-D07 devcontainer configuration/lifecycle/features, C01-C04 Compose projection, F01 failure recovery and V01 real VS Code. None may disappear because an adapter is incomplete. The release result must enumerate every expected fixture and assertion and reject omissions, skips, duplicate results or retry-only passes.

Before removing old entry points:

1. Connect the complete verified release/runtime closure, including guest images, Docker VM/oracle, official CLI and VS Code pins. Download GitHub releases; do not invoke SwiftPM or another product build in a parity case.
2. Add strict preparation and one-case adapters for all 19 fixtures, porting useful assertions without retaining lane-wide rebuilds or destructive evidence resets.
3. Connect the shared runtime lease and marker-protected SSD roots; journal owned resources before creating them. Recover an interrupted case only after confirming worker identity and reconciling its owned resources.
4. Retain case evidence internally before cleaning SSD scratch. Generate JSON, JUnit and the human comparison matrix from those same records.
5. Exercise cancellation, deadlines, crash-before/after-seal, corrupt receipts, changed artifacts, cleanup failures and repeated no-change unit requests. Prove completed cases are not unnecessarily re-executed and failed attempts remain visible.
6. Run exact-inventory differential parity against real Docker, stock Apple Container and the enhanced stack. Run at least five quiet paired timing samples; preserve timeout and 10x regressions. Retire the old harness only when the replacement meets these gates.

The present work does not change a support claim, lower the 90% coverage target, qualify a stable release or replace protected CI checks.
