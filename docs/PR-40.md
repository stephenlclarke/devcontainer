# Change handoff: bound and clean up the private provider transport

## Summary

Move the gateway's private provider-session socket to a deterministic short,
user-scoped directory, validate and remove its expected shutdown artifacts, and
pin Container Engine API v0.3.3 for chunked provider request bodies.

## Motivation

The previous state-relative socket could exceed Darwin's Unix-socket path limit
in long hosted workspaces. A short path closes that startup failure, but unique
test sockets must not leave persistent lock directories. The adopter also needs
Engine protocol v3 so large BuildKit image-load requests are divided into
bounded frames instead of rejected as one oversized JSON frame.

## Implementation

- Hash the public socket with SHA-256 and use the first 12 bytes to derive
  `/tmp/devcontainer-engine-<uid>-<digest>/provider.sock`.
- Keep the private path below 104 bytes regardless of the public socket length.
- Route both the provider server and public gateway responder through the same
  derived socket.
- After an orderly gateway shutdown, require an owner-only directory, no live
  socket, and exactly one owner-only, single-link regular lock file before
  removing the lock and directory.
- Preserve unexpected or unsafe entries and return a state-corruption error
  instead of deleting them.
- Leave standalone `--provider-socket` ownership with its caller; only the
  internally generated gateway socket is cleaned by the service.
- Pin Container Engine API exactly to v0.3.3.

## Security and cleanup invariants

- A 96-bit digest makes accidental path collision negligible while keeping the
  path bounded.
- The Engine provider listener continues to enforce owner identity, file type,
  `0700` directory mode, `0600` socket/lock mode, no symlink following, single
  link count, and an exclusive advisory lock.
- Cleanup runs only after the provider listener releases the socket and lock.
- Cleanup never recursively removes a directory and never removes unexpected
  content.
- A public-listener shutdown failure still stops the provider and attempts safe
  artifact cleanup before propagating the original error.

## Validation

```console
swift test --disable-automatic-resolution \
  -Xswiftc -warnings-as-errors --filter DevContainerServiceTests
SWIFT_COVERAGE_BASE=origin/main SWIFT_TEST_ATTEMPTS=1 make check
DEVCONTAINER_CONTAINER_BIN=/usr/local/bin/container \
  Tools/parity/run-lane.sh apple-stock .build/parity-engine-v033-final
DEVCONTAINER_CONTAINER_BIN=/opt/homebrew/opt/container/bin/container \
  DEVCONTAINER_COMPOSE_BIN=/opt/homebrew/opt/container-compose/bin/container-compose \
  Tools/parity/run-lane.sh container-compose .build/parity-engine-v033-final
```

Results:

- Focused service suite: 7 tests passed.
- Complete closure gate: 202 Swift tests in 18 suites passed; first-party line
  coverage was 95.38%; all source, tooling, docs, and manifest gates passed.
- Stock Apple lane: 18 of 18 fixtures passed with no cleanup differences.
- Stable container-compose lane: 17 of 18 fixtures passed with no cleanup
  differences. `D05-features` passed in 32.579 seconds with `feature_git`,
  `feature_jq`, `frozen_lock`, and `lockfile` all true.
- The only stable-compose failure is `C04-compose-lifecycle`, already tracked in
  container-compose issue 184.
- No private provider directory remained under `/private/tmp` after the final
  lanes.

## Compatibility

Public Docker API paths, state ownership, provider fingerprints, and explicit
standalone provider sockets are unchanged. The dependency change adopts Engine
provider protocol v3; the private protocol is version-locked on both ends and is
not a public compatibility surface.

## Linked issue

Closes [#40](https://github.com/stephenlclarke/devcontainer/issues/40).

## Remaining risk

The stable container-compose runtime still lacks complete force-recreate and
network-alias semantics for `C04`; that is a separate matched-runtime gap, not a
regression in this transport change.
